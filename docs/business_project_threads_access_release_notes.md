# Business プロジェクト内スレッド・参加承認/アクセス管理 リリースメモ

ブランチ: `feature/business-project-threads-and-access-control`

## 変更概要

- プロジェクト内に複数のスレッド(`project_threads`)を作れるようにした。投稿(`project_chats`)はスレッドに紐づく。
- コミュニティ・プロジェクトそれぞれに参加方式(`join_approval_mode`: 0=手動承認 / 1=自動承認)を追加。
- プロジェクトの承認待ち(`project_join_requests`)、コミュニティ・プロジェクトのアクセス停止(`*_access_suspensions`)を追加。
- 権限判定は `BusinessAccess`(Customer に include)に集約。コントローラ側の取得・リダイレクトは `BusinessAccessControl`。

## 所属状態の扱い

- 承認済み = `community_customers` / `project_members` の行。承認待ち = `permits` / `project_join_requests`。
- 却下・本人の取り消し = 承認待ちの行を削除(再申請できる)。
- アクセス停止 = 参加・承認待ちを削除し `*_access_suspensions` を作成(手動・自動どちらでも再参加不可)。解除しても参加資格は戻らない(再度の参加・申請が必要)。
- コミュニティの参加資格が外れる(本人の退会・運営者の停止)と、配下プロジェクトの参加・承認待ちも削除する。再参加時(承認・自動参加)にも配下プロジェクトの残存行を削除するため、過去のプロジェクト参加資格は復活しない。プロジェクトのアクセス停止は残る。
- 承認方式を変更しても、承認待ち・参加済みは変更しない(変更後の新しい申請から適用)。

## マイグレーション

どれも途中で失敗しても再実行できる(MySQL の DDL は巻き戻らないため、列・テーブル・索引・「全体トーク」をそれぞれ存在確認してから作る)。

1. `20261027000000_add_join_approval_mode_to_communities_and_projects`
   - communities: 既存・新規とも手動承認(0)。従来の Business コミュニティは「申請 → 承認」だったため。
   - projects: 既存行は自動承認(1)。従来は「コミュニティ参加者なら即参加」だったため。新規作成の既定値は手動承認(0)。
2. `20261027000100_create_business_membership_tables`: 新規テーブル3つ(一意制約・外部キー付き)。既存データは変更しない。
3. `20261027000200_create_project_threads`
   - 既存プロジェクトごとに「全体トーク」(`general = true`)を作り、既存の `project_chats` を紐づける(`project_thread_id` のみ更新。本文・投稿者・日時・添付は変更しない)。
   - `(project_id, general)` の一意制約で、全体トークは1プロジェクトに1つだけ(通常のスレッドは `general = NULL` で制約の対象外)。
   - `project_thread_id` は NULL 許容のまま(マイグレーション後〜Puma 再起動前に旧コードが書き込む行で失敗させないため)。
   - `project_threads.customer_id`(作成者)は NULL 許容(作成者の会員データを完全削除してもスレッドを残すため)。
4. `20261027000300_allow_null_project_creator`: `projects.customer_id` を NULL 許容に(作成者の完全削除でプロジェクトを消さないため)。既存行は変更しない。

ローカル MySQL の使い捨て DB(main のスキーマ + 旧データ)で、4本の実行、途中失敗を想定した再実行、旧コード相当の書き込み、全体トークの同時補完(4接続)、backfill・audit を確認した。生成されたスキーマは `db/schema.rb` と一致。DDL が途中まで適用された場合の扱いは「デプロイ失敗時・切り戻し」を参照。

`community_customers` / `permits` は music と共用のため一意制約を追加していない。Business 側の参加・承認はコミュニティ行のロック(`with_lock`)で直列化して重複を防ぐ。

## デプロイ前の影響確認(読み取り専用)

`script/business_access_preflight.rb` は、現行本番のコード・スキーマ(切り替え前)でも動くよう、アプリのモデルや新しいテーブルに依存せず既存テーブルだけを SQL で参照する。書き込みは Rails(`while_preventing_writes`)と MySQL(`SET SESSION TRANSACTION READ ONLY`)の両方で禁止し、最後に ROLLBACK する。出力は件数と ID だけ(氏名・メールアドレスは出さない)。

本番では未デプロイのファイルなので、スクリプトを一時ディレクトリへ置いて実行する(要ユーザー確認):

```bash
# 手元から(リポジトリの外の一時ディレクトリへ。デプロイ先ディレクトリには置かない)
scp script/business_access_preflight.rb ec2-user@<host>:/tmp/business_access_preflight.rb
# 本番サーバー上
cd /home/ec2-user/be-my-style
RAILS_ENV=production bundle exec rails runner /tmp/business_access_preflight.rb
RAILS_ENV=production DETAIL=1 bundle exec rails runner /tmp/business_access_preflight.rb   # 対象の ID 一覧
rm /tmp/business_access_preflight.rb
```

見る項目:

| 出力 | 意味 |
|---|---|
| プロジェクト参加者のうち、コミュニティ参加資格が無い人 `rows / communities / projects / customers` | 切り替え後にプロジェクト内部を閲覧できなくなる行・コミュニティ数・プロジェクト数・人数 |
| コミュニティ参加資格が無いプロジェクト作成者 | 切り替え後はプロジェクト管理者として扱わない作成者 |
| `withdrawn` | 退会済み。ログインできないため影響なし。**承認しない** |
| `community_suspended` | (切り替え後のみ)コミュニティのアクセス停止中。**承認しない** |
| `unconfirmed` | メール未確認でログインできない。承認不要 |
| `permit_pending` | コミュニティへ申請中。運営者が通常の承認画面で判断する |
| `not_in_community` | 申請も無い。旧コードではコミュニティを退出・除外されてもプロジェクトの行が残ったため、**本人の退出・運営者の除外である可能性が高い**。一括承認せず運営者が個別に判断 |
| `duplicate_*` / `permits_of_existing_members` | 重複行・参加済みなのに残っている申請(0 が正常) |
| `communities_without_active_manager` | 承認できる運営者(退会していない owner / 共同運営者)がいないコミュニティ |

対応案(本番データは変更しない前提で、結果を見て判断):

- 0 件 → そのまま切り替える。
- `not_in_community` が少数 → 運営者に対象 ID を共有し、必要な人だけ「参加申請 → 承認」の通常手順で戻してもらう(一括承認はしない)。
- 多数・重要なプロジェクトに偏る → 切り替え前に運営者へ告知するか、リリースを延期して対応方針を決める。
- `communities_without_active_manager` が 0 でない → 承認できる人がいないため、admin による対応方針を先に決める。

### 旧コードとの共存

`git reset` から Puma 再起動までの間(bundle・precompile を含め数分)、動作中の Puma は旧コード、ディスク上は新コードになる。DB は migrate までは旧スキーマ、migrate 後(〜Puma 再起動の十数秒)は新スキーマ。

| 期間 | 旧 Puma がしたこと | 影響 | 新コードでの扱い |
|---|---|---|---|
| reset 〜 migrate | まだ表示していない画面を初めて表示 | ディスク上の新しいテンプレートを読む可能性がある(推定・下記)。今回変更したプロジェクト画面・コミュニティ画面などは新しいヘルパー・ルートを使うため、その画面だけ一時的にエラーになり得る | 再起動後は解消 |
| migrate 中・後 | スレッド未指定で投稿 | `project_thread_id` が NULL の行になる(投稿は成功) | 自動補完で「全体トーク」へ紐づく |
| 同上 | プロジェクトを作成 | 「全体トーク」が無い。参加方式は DB 既定の手動承認 | 自動補完で「全体トーク」を作る。利用者がスレッドを作る必要は無い |
| 同上 | 通知・メールを送信 | 旧 URL(`/business/projects/:id`)。通知は本文なし | 新コードのプロジェクト画面で権限を確認して表示 |
| 同上 | プロジェクト削除・会員の完全削除 | `project_threads` の外部キーで失敗しロールバック(データは消えない) | 再起動後に再操作 |
| 同上 | 参加・承認・退出 | 既存テーブルだけを使うため従来どおり(停止テーブルは空) | そのまま有効 |
| migrate が途中で失敗した状態 | 上と同じ。どの段階で止まっても旧コードは動く(追加した列は既定値あり・NULL 許容、テーブルは参照しない) | 削除系だけ外部キーで失敗し得る | 再実行で残りを適用 |

権限への影響: 今回追加するアクセス停止・閲覧制限は新コードでしか効かないが、共存期間中は停止データがまだ存在しない(テーブルが空)ため、リリース前より弱くなる操作は無い。新コードの Puma が起動した後に初めて停止・制限が使われる。

**危険なのは逆の組み合わせ(新コード + 未マイグレーションの DB)**。デプロイ処理は migrate が完了・確認できるまで Puma を再起動しないが、デプロイ失敗後に**外から Puma が再起動された場合**(EC2 夜間自動停止からの朝の起動・手動 restart・Puma マスターの異常終了による systemd の再起動)は新コードで起動する。ローカル検証では、会員・コミュニティ・音楽側は動くが、プロジェクト画面・プロジェクト作成・投稿は `project_threads` が無いためエラーになった(閲覧制限は失敗する側=表示しない側に倒れる)。デプロイが失敗したら、夜間停止(JST 2:00)より前に再実行で復旧させる。

### 自動補完(全体トークの作成・未所属投稿の紐づけ)

- **実行タイミング**: 新コードでプロジェクト画面(内部を閲覧できる人)・スレッド一覧・スレッド画面を開いたとき、旧導線(`/business/projects/:id/project_chats`)から投稿したとき、新規プロジェクト作成時、`rails business_project_threads:backfill` 実行時。補う必要が無ければ問い合わせ2回で終わる。
- **重複しない理由**: 全体トークは `(project_id, general)` の一意制約で DB が2つ目を拒否する(同時に作ろうとした側は既存の全体トークを使う)。補完はプロジェクト行のロックで直列化し、スレッド削除も同じロックを取る。紐づけは `project_thread_id` を NULL から更新するだけで投稿を作らない。
- **会話を混ぜない**: 未所属の投稿は、そのプロジェクトの全体トークにだけ入れる(別の話題のスレッドがあってもそこへは入れない)。全体トークは削除できないため、送り先が消えることもない。
- **失敗したとき**: そのプロジェクトの処理はトランザクションごと巻き戻る(投稿・添付は変更されない)。画面は表示し、「一部の過去の投稿を表示できていない可能性があります(投稿は削除されていません)」と「再読み込みする」ボタンを出す(再読み込み=再試行)。ログに `[Business::ProjectThreads::LegacyChatBackfill] failed project_id=...` を出す。
- **検知と復旧**: 上記「コマンド1」で失敗ログを確認(既存の運用は `journalctl` だが、Rails のログはファイルに出ている可能性がある) → `business_access:audit` の `unthreaded_project_chats` / `business_projects_without_general_thread` と対象 `project_ids` を確認 → 原因(ロック待ち等)を確認して `business_project_threads:backfill` を実行(残りがあると終了コード 1。何度でも再実行可) → audit が 0 になれば復旧。エラー監視サービス(Sentry 等)は導入されていないため、自動通知は無い。

## デプロイ失敗時・切り戻し

### デプロイ失敗時(再実行で復旧できる条件と手動対応が必要な条件)

前提: デプロイ処理の改善(別 PR)がマージ済み。差分の基準が「最後に成功したデプロイ」になり、migrate は毎回実行され、Puma は migrate・precompile の成功後にだけ再起動される。`spec/deploy/production_deploy_script_spec.rb` で、各段階で失敗させてから同じコミットで再実行し、復旧することを確認した(疑似サーバー。本番には接続していない)。同じ検証を main のワークフローに当てると、precompile 失敗・migrate 途中失敗の後の再実行が「成功」と表示されたまま、未マイグレーションの DB で新コードの Puma が起動することを再現した。

| 失敗した段階 | 失敗直後の状態 | 再実行で復旧する条件 | 手動対応が必要な条件 |
|---|---|---|---|
| SSH 接続・git fetch | 何も変わらない | 接続が戻れば復旧(夜間停止中は朝に再実行) | — |
| bundle / yarn | 旧 Puma・旧 DB・ディスクは新コード | ネットワーク等の一時的な原因なら復旧 | Gemfile.lock・ネイティブ拡張の問題 → 修正 PR |
| assets:precompile | 同上(DB は変更していない) | 一時的な原因なら復旧。メモリ不足ならスワップ確保後に再実行 | SCSS/JS の誤り → 修正 PR(PR CI でも precompile する) |
| db:migrate の途中 | 旧 Puma・DB は途中まで新スキーマ | 接続断・ロック待ち等の一時的な原因なら、残りだけ適用して復旧(4本とも途中から再実行できることを確認済み) | マイグレーション自体の誤り・データ起因の失敗 → 原因を確認し修正 PR(DB を手で直さない) |
| migrate 後、Puma 再起動前(sudo 失敗・接続断) | 旧 Puma・新 DB | migrate は空振りし、Puma を再起動して復旧 | — |
| Puma が起動しない | **サイト全体が停止(502)** | 一時的な原因(メモリ不足等)なら復旧 | 新コードが起動できない → 修正を急ぐか、下記「切り戻し」を判断 |
| Puma は起動したが `GET /` が異常・CSS が 404 | 新コードで動作中だが異常 | CSS は再実行で precompile をやり直す | アプリのエラー → 修正 PR か切り戻しを判断 |
| singing-analyzer | Rails 側は新コードで正常 | 一時的な原因なら復旧 | requirements.txt の問題 |

### MySQL の DDL が途中まで適用された場合

- MySQL の DDL はトランザクションで巻き戻らず、Rails も MySQL ではマイグレーションをトランザクションで囲まない。マイグレーション1本の中で文ごとに確定し、`schema_migrations` への記録はその1本の全処理の後。途中で止まると「一部の列・表・索引だけある、未適用扱い」の状態になる。1つの DDL 文自体は MySQL 8.0 以降なら途中まで適用されることはない(アトミック DDL)。
- 4本とも、列・表・索引・外部キー・「全体トーク」をそれぞれ存在確認してから作るため、どこで止まっても再実行で残りだけを作る。ローカル MySQL(9.6)の使い捨て DB(main のスキーマ + 旧データ)で、7か所(列追加の間・既定値変更の前・表作成後の索引・`add_reference` の列追加後と外部キーの前・全体トーク作成ループの途中)で失敗させてから再実行し、失敗なしの場合とスキーマ・データ(全体トーク・紐づけ・参加方式)が一致することを確認した。
- この検証で、`add_reference`(列・索引・外部キーを別々の文で作る)の途中で止まると、再実行で列があるため丸ごと飛ばされ、**外部キーが無いまま「成功」になる**ことが分かったため、列・索引・外部キーを個別に確認して作る形に直した(できあがるスキーマは修正前と同一で、`db/schema.rb` と一致)。
- 外部キーの追加(`ALTER TABLE ... ADD CONSTRAINT`)は表のコピーを伴い、既存行の外部キーも検査される。本番の `project_chats` に親の無い行(参照先の会員・プロジェクトが無い)があると失敗する。外部キーは以前から張られているため通常は無い。影響確認スクリプトの実行時に合わせて確認できる(下記「本番反映前の確認」)。

### ロック待ちの上限(マイグレーションの接続だけ)

- 本番の `lock_wait_timeout` は 31536000 秒(既定値・1年)。ALTER はテーブルのメタデータロックを待ち、待っている間は同じ表への後続の問い合わせもその後ろで止まる。長いトランザクションが残っていると migrate もサイトのその表を使う画面も止まり続ける。
- そこで 4 本のマイグレーションは、実行中だけ自分の接続に `SET SESSION lock_wait_timeout = 5, innodb_lock_wait_timeout = 10` を設定し、終了時(失敗時も)元の値に戻す(`lib/migration_lock_wait_timeout.rb`)。サーバー全体(GLOBAL)・パラメータグループは変更しない。
- MySQL 8.0 以降、外部キーでつながる表のロックも取るため、`projects` の ALTER は `project_chats` を使うトランザクションでも待つ(ローカルで確認)。
- 時間切れのとき: そのマイグレーションは失敗し `schema_migrations` に記録されない。デプロイは migrate で止まり、Puma は再起動されない(旧コードのまま動く)。4 本とも途中から再実行できるため、待ちの原因(長いトランザクション)が終わってからデプロイを再実行すれば残りだけ適用される(デプロイ処理は migrate を毎回実行する)。繰り返し失敗する場合は `SHOW PROCESSLIST`(読み取り)で長く続いている接続を確認する。
- ローカル MySQL 9.6 で確認済み: 実行中だけ 5/10 秒になり終了後に元へ戻る / communities を読むトランザクションが残ると約 5.1 秒で失敗・未記録 / 3 本目の途中で失敗 / 既存チャットの行ロックで約 10 秒で失敗 / いずれも解消後の再実行で、失敗なしの場合とスキーマ・データが一致 / GLOBAL は不変。比較として上限を外すと、ALTER が「Waiting for table metadata lock」のまま 390 秒以上待ち続けた。

### 切り戻し(コードを旧版へ戻す)の方針

**切り戻しは安全側の対応ではない。** 旧コードは今回の権限チェックを持たないため、戻すと次の制限が効かなくなる(DB の停止・承認待ちのデータは残るが参照されない)。

| 戻すと効かなくなる制限 | 旧コードでの挙動 |
|---|---|
| プロジェクトだけのアクセス停止 | コミュニティ参加者なら「参加する」で即時に再参加でき、投稿を読める |
| コミュニティのアクセス停止 | 参加データは削除済みのため内部は見えないが、再申請でき、運営者が承認すれば戻る(停止中の表示は無い) |
| コミュニティ参加資格の無いプロジェクト参加者の閲覧制限 | コミュニティを退出・除外された人も、プロジェクトの行が残っていれば投稿・添付を閲覧・投稿できる |
| プロジェクトの参加方式(手動承認)・承認待ち | 無視され、コミュニティ参加者は即時参加 |
| プロジェクトの編集・更新の権限 | **権限チェックが無い**(ログイン中の会員ならプロジェクトを編集できる) |
| プロジェクト概要・メンバー一覧の閲覧制限 | ログイン中の会員なら他コミュニティのプロジェクトも閲覧できる(投稿はプロジェクト参加者のみ) |
| タイムライン(本文・添付)の参加者限定 | ログイン中の会員なら閲覧できる |
| 送信待ちメールの権限再確認 | 確認せずに送る |

データへの影響: 追加した列・テーブルは旧コードから参照されない。切り戻し中の投稿は `project_thread_id` が NULL、作成されたプロジェクトは全体トーク無しになり、再デプロイ後に自動補完で全体トークへ入る(消えない)。プロジェクト削除・会員の完全削除は外部キーで失敗する。DB を戻す(`db:rollback STEP=4`)とスレッド・申請・停止のデータが失われ、作成者が完全削除されたプロジェクトがあると失敗するため、行わない。

優先順位:

1. **権限を保ったまま直す(修正して再デプロイ)。** デプロイ処理の失敗なら原因を直して再実行。アプリの不具合なら hotfix ブランチ → PR → マージ(通常のフロー)。
2. **Business だけ一時的に閉じる。** 不具合が Business に限られ、修正に時間がかかる場合。Nginx で `/business` 配下を 503(メンテナンス表示)にする案が、権限を弱めずに他の機能を動かせる(Nginx 設定の変更・reload は要ユーザー確認。設定は本リポジトリ管理外のため、手順は事前に確認が必要)。
3. **コードの切り戻し。** 新コードで Puma が起動できずサイト全体が止まり、1・2 で短時間に復旧できない場合に限る。**戻すと上の表の制限が効かなくなるため、2 と組み合わせて Business を閉じた状態で戻す**ことを推奨。停止・承認待ちのデータが既に作られている(=新コードが動いていた時間がある)場合は特に、Business を開けたまま戻さない。

切り戻しの手順(要ユーザー確認): 本番サーバーで `git checkout <旧コミット>` → (Business を閉じる場合は Nginx 設定) → `sudo systemctl restart puma`。DB は戻さない。旧コードのアセットは precompile 済みのファイルが残っているが、念のため `RAILS_ENV=production bundle exec rails assets:precompile` を実行してから再起動する。復旧後に main へ修正をマージすると、次の自動デプロイが新コードへ戻す(切り戻したコミットからの差分も判定に含めるため、必要な処理は実行される)。

**対象 DB の見分け方**

  ```bash
  sudo systemctl show puma -p Environment --value | tr ' ' '\n' | sed -n 's/^"\{0,1\}DB_HOST=\([^.]*\)\..*/\1/p'
  ```

- コンソールでは、リージョン「アジアパシフィック(東京)」の RDS →「データベース」で、その識別子の行を選ぶ。「接続とセキュリティ」タブのエンドポイントが `DB_HOST` と一致し、「設定」タブのエンジンバージョンが **8.4.8** であることを確かめてから、バックアップの確認・スナップショットの取得を行う。読み取り用のレプリカやほかの DB と取り違えないため、識別子だけで判断しない。

**マージ直前の手動スナップショット(要ユーザー確認。まだ取らない)**

1. 夜間停止(JST 2:00〜6:00)と利用の多い時間帯を避け、マージの直前に取る。
2. コンソール: 対象インスタンス →「アクション」→「スナップショットの取得」→ 名前(例 `bms-before-business-threads-20261028`)。CLI: `aws rds create-db-snapshot --db-instance-identifier <id> --db-snapshot-identifier bms-before-business-threads-<日付>`。
3. 完了確認: 状態が「利用可能」(`available`)になるまで待つ(`aws rds wait db-snapshot-available --db-snapshot-identifier <名前>`、または `describe-db-snapshots` の `Status`)。シングル AZ の MySQL では取得開始時に短い I/O の停止が起き得る。完了を確認してからマージする。
4. 手動スナップショットは削除するまで残り、保管料金がかかる。不要になったら削除する。

**復元時の注意**

- スナップショット・ポイントインタイムリカバリのどちらでも、**復元は新しい DB インスタンスとして作られる**(既存のインスタンスは上書きされない)。エンドポイントが変わるため、接続先(systemd の `DB_HOST`)の切り替え・`daemon-reload`・Puma 再起動が必要。パラメータグループ・セキュリティグループ・インスタンスクラスは復元時に指定し直す。
- スナップショット以降の書き込み(Business 以外も含む全機能)は失われる。
- 今回のマイグレーションは既存データを書き換えない(列追加・表追加・`project_thread_id` の設定・NULL 許容化のみ)ため、復元が必要になる場面は想定していない。最終手段として扱う。

## 退会・会員データ削除時

- 退会(管理画面で `is_deleted`)では何も削除しない。作成したスレッド・投稿・添付は残り、名前は「退会済みユーザー」と表示。通知・メールの宛先から外れ、ログインもできない。
- 会員データの完全削除(管理画面の「完全退会」)でも、作成したプロジェクト・スレッドは残す(`projects.customer_id` / `project_threads.customer_id` を NULL にし「退会済みユーザー」と表示)。作成者なしのプロジェクトはコミュニティ運営者・admin が引き続き管理でき(引き継ぎ操作は不要)、ほかの参加者は従来どおり閲覧・投稿できる。Project は Business でしか使っていないため、音楽側への影響は無い。
- 残る制約(今回の変更前から同じ。main でも同じ結果を確認): 投稿(`project_chats` / `community_posts`)がある会員の完全削除は外部キーで失敗し、ロールバックされる(部分削除は起きない。画面はエラーになる)。投稿をどう扱うか(削除する・匿名化する)は方針判断のため変更していない。案: 管理画面の「完全退会」の前に、その会員の Business 投稿数・作成プロジェクト数・作成スレッド数を表示し、投稿がある場合は「退会(is_deleted)」を案内する。

## アクセス停止後の経路

- 投稿・スレッド・件数・メンバー: すべてリクエストごとに `BusinessAccess` で判定するため、停止・退出の直後から閲覧できない。プロジェクト投稿・タイムラインを対象にした検索は無い。
- 通知: 本文を含まない(「〜がコメントしました」とリンクのみ)。リンク先で権限を確認する。
- メール: 送信済みのメールに含まれる本文は取り消せない。送信待ち(`deliver_later`)のメールは送信時に閲覧権限を再確認し、停止・退出・退会した人には送らない。リンクはログインと権限確認が必要。
- 添付: 画面には権限確認付きの URL(`/business/chat_attachments/:id`)だけを出す。アクセスのたびに権限を確認し、S3 の署名付き URL(有効期限 5 分)へリダイレクトする。**発行済みの署名付き URL は個別に無効化できず、発行から最大 5 分間は取得できる**(停止前に開いていたファイルの URL を控えていた場合)。停止後に新しい URL は発行されない。即時遮断が必要な場合は、その添付の blob を削除する(投稿からも消える)か、S3 のキー自体を差し替える必要がある。
- リアルタイム配信: Business のチャットは Action Cable を使っていない(チャンネル定義なし)ため、該当経路は無い。

## 仕様変更(意図したもの)

- Business コミュニティのタイムライン(本文・添付)は、従来「ログイン中の会員なら閲覧可」だったが、コミュニティ参加者(運営者を含む)のみに変更。
- Business トップ・プロジェクト一覧は、参加中・運営中のコミュニティのプロジェクトだけを表示。
- プロジェクトの編集・更新は、従来権限チェックが無かったため、プロジェクト管理者のみに限定。所属コミュニティはパラメータで変更できない。
- プロジェクト作成者・コミュニティ運営者は、プロジェクトに参加していなくてもスレッドを閲覧・投稿できる(従来は作成者でも参加しないとチャットを閲覧できなかった)。
