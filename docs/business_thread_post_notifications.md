# Business スレッド投稿の通知

Business プロジェクトのスレッドに投稿したときの、画面内の通知とメールの仕様・保証範囲・リリース時の注意点。

## 通知先

`BusinessAccess#business_project_notification_recipient?` で1人ずつ判定する(メールの送信時も同じ判定)。

| 対象 | 通知 |
|---|---|
| プロジェクトの承認済み参加者(親コミュニティにも参加) | 届く |
| 主催(親コミュニティに参加しているプロジェクト作成者) | 届く |
| 参加している運営者(コミュニティ運営者・共同運営者) | 届く |
| 投稿者本人 | 届かない |
| 承認待ち・退出・アクセス停止(プロジェクト / コミュニティ)・退会済み | 届かない |
| 参加していない運営者・システム管理者(管理権限だけ) | 届かない |
| 別プロジェクトの参加者 | 届かない |

対象の投稿は本文・添付だけ・スタンプ(旧導線の全体トークへの投稿を含む)。リアクションは対象外。

## 画面内の通知

- `notifications.action = "project_message"`、`project_chat_id` に投稿を持つ。
- 一覧には投稿者名と「コミュニティ / プロジェクト / スレッド」を出す。本文・添付の URL は出さない。
- リンク先は `/business/projects/:id/threads/:thread_id#post-project_chat-:id`(該当投稿へスクロールして目印を付ける)。スレッド画面は従来どおりサーバー側で参加資格を確かめる。
- いまプロジェクト内部を閲覧できない場合は「閲覧できなくなったプロジェクトの通知です」とだけ出し、名前・リンクを出さない。`project_chat_id` が NULL の旧通知も同じ。
- 参加通知(project_joined)など、ほかの種類の表示・リンクは変えていない。

## メール

- `BusinessProjectChatMailer#thread_post_mail`。引数は通知 ID だけ。送信時に通知を読み直す。
- 通知は投稿・スレッド・プロジェクト・宛先・投稿者の削除と一緒に消えるので、見つからなければ送らない(例外にしない)。
- 送信時に宛先の参加資格(退出・停止・退会)とメール受信設定を確かめ直す。
- 本文入りのメールは既存仕様のまま(参加資格を確かめてから送る)。リンクは該当スレッドの該当投稿。
- 更新前の形式のジョブ(`CustomerMailer#business_project_chat_mail`、投稿・会員を直接渡す)は互換のため残し、同じ確認とリンクを追加した。本番のジョブは Puma 内で動く async 方式で、再起動で送信待ちのジョブは消えるため、デプロイ後に旧形式のジョブが新しいコードで動くことは通常ない。なお旧形式で送信前に投稿などが削除された場合は、従来どおりジョブが引数の読み込みで失敗する(再試行は無い)。

## 重複防止と送信タイミングで保証できる範囲

| 項目 | 保証 |
|---|---|
| 画面内の通知 | 同じ投稿・同じ宛先は DB の一意制約 `(project_chat_id, visited_id)` で必ず1件。再実行・同時実行でも同じ(MySQL 8.4.8 で8本同時実行を確認) |
| メールの登録タイミング | 通知の保存がコミットされた後だけ(`after_create_commit`)。巻き戻った通知・一意制約で弾かれた重複では登録しない |
| メールの重複 | このコードから登録するのは、通知を新しく作れた1回につき1件だけ。同じ投稿・同じ宛先へ2件目を登録することはない |

一意制約がメールの重複・取りこぼしまでは保証しない点:

- 通知の作成後にメールの登録が失敗した場合(キューの異常など)、投稿と通知は残り、エラーログに通知 ID を残す。再実行しても通知は既にあるので作り直さず、**そのメールは送られない**(重複より取りこぼしを選んでいる)。
- async 方式のため、メールの登録後、送信前に Puma が再起動すると、そのメールは送られない。
- 送信済みかどうかは記録していない。同じジョブが2回実行されれば2通送られ得る(現状の async 方式には自動の再試行が無いため、通常は起きない)。

## DB 変更(20261101000000_add_project_chat_to_notifications)

`notifications.project_chat_id`(bigint、NULL 許容)と一意索引 `index_notifications_on_project_chat_id_and_visited_id` を追加する。既存の通知は NULL のまま変わらない(NULL 同士は一意制約で重複にならない)。外部キーは付けない(MySQL は外部キーの追加で表をコピーするため)。投稿の削除時は `ProjectChat has_many :notifications, dependent: :delete_all` で消す。

MySQL では方式を明示し、使えない場合は表をコピーせずにエラーで止まる。

| DDL | 方式 | 内容 |
|---|---|---|
| 列追加 | `ALGORITHM=INSTANT` | 表を書き換えない(データ辞書の変更だけ) |
| 一意索引 | `ALGORITHM=INPLACE, LOCK=NONE` | 作成中も通常の読み書きは続けられる |

**ロックについて:** どちらの DDL も、開始時と終了時に短時間の排他メタデータロックを取る。notifications を使う長いトランザクションが残っていると、その終了を待つ間、後続の notifications への問い合わせ(通知一覧・ベルの件数・通知の作成など)もその後ろで待たされる。待ちは `MigrationLockWaitTimeout` で5秒(行ロックは10秒)に制限し、超えたらこのマイグレーションは失敗する(schema_migrations に記録されない)。原因のトランザクションが終わってから `db:migrate` をやり直せばよい(列・索引の有無を確認してから追加するので、途中まで適用済みでも再実行できる)。

INSTANT の列追加は、表ごとに行バージョンの上限(64)がある。上限に達している表では INSTANT が使えずエラーで止まる(表は変更されない)。本番の値は未確認で、必要なら読み取り専用で次を確認する。

```sql
SELECT TOTAL_ROW_VERSIONS FROM information_schema.INNODB_TABLES WHERE NAME = '<DB名>/notifications';
```
